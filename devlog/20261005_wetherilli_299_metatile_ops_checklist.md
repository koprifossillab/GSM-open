# 메타타일 첫 운영 점검표 — 하루 뒤에 볼 것, 되돌리는 스위치

2026-10-05 · `feature/metatile-ops` · wetherilli

v0.60.0 이 나가면 운영에서 메타타일(wetherilli 282·284·287)과 응답 시간 열(290)이 처음 돈다. 배포하고 **하루쯤 뒤**에 이 표대로 본다.
운영은 읽기만 한다. 2026-10-05 의 앞값(v0.59.0)은 wetherilli 297 에 있다 — 캐시 1.4 GB·45 734 개, 하루 평균 110 MB, `locks/` 없음.

메타타일 레이어(`views.METATILE`) — 멕시코 지자기 `sgm:datos:7`, `sgc:sa:`·`sgc:co:`(줌 6 까지), `egdi:`, `gssa:`, `iige:`, `ispra:1m:`, `mris:`,
`pig:`, `sgs:`, `dinamige:`, `lneg:500k:`, `tno:`, `swisstopo:`, `segemar:`, `gsi:1m:`.

## 1. `upstream_stats` 로 볼 것

```
docker exec gsm-web-1 python manage.py upstream_stats --days 2
```

- **응답 시간이 찍히는가** — 아래 요약에 상류마다 잰 건수·평균·p95 가 서야 한다. 비어 있으면 0045 가 안 돌았거나 문이 `elapsed` 를 넘기지 않는 것이다
- **메타타일 상류의 평균이 1 024 px 한 장 값인가** — 칸 하나보다 길어야 정상이다(멕시코 지자기 20 초 남짓, 아일랜드 3 초). 대신 **건수**가
  화면이 부른 칸 수의 1/4 언저리여야 한다. 건수가 칸 수와 비슷하면 격자가 맞지 않아(`tile_of` 가 `None`) 칸 하나씩 받고 있는 것이다
- **p95 가 `>34` 인 상류** — 메타타일 한 장이 문의 시간 한계(대개 45 초, 멕시코 90 초, 아일랜드 20 초)에 걸릴 수 있다. 실패하면 칸 하나로
  되받으므로(`errors`) **실패 하나에 호출이 둘**이다 — 실패 칸이 그 상류 건수의 10 % 를 넘으면 그 상류를 표에서 빼는 것을 생각한다
- **차단 조짐**이 하나라도 있으면 아래 3 의 스위치부터 본다. 큰 장은 상류에 무거운 요청이다

## 2. 캐시·`locks/` 에서 볼 것

```
find /data/GSM/tiles/locks -type f | wc -l                       # 받은 메타타일 수 (잠금 파일은 블록마다 하나, 0 바이트)
find /data/GSM/tiles/locks -type f -newermt '-1 day' | wc -l      # 지난 하루
find /data/GSM/tiles -name '*.part' | wc -l                       # 0 이어야 한다
du -sh /data/GSM/tiles
docker logs --since 24h gsm-web-1 2>&1 | grep -c '메타타일 .* 잘라 담았다'
docker logs --since 24h gsm-web-1 2>&1 | grep -c '칸 하나로 되받는다'
docker logs --since 24h gsm-web-1 2>&1 | grep -E 'WORKER TIMEOUT|타일을 캐시에 두지 못했다|더 담지 않는다'
```

- `locks/` 가 생겼으면 메타타일이 돈 것이다. 잠금 파일은 **지우지 않는다** — 받는 동안 다른 워커가 그 파일로 기다린다. 블록마다 0 바이트
  하나라 4 만 블록이어도 아이노드만 쓴다
- "잘라 담았다" 하나에 조각 넷(512 px 칸)이다. "되받는다" 가 "잘라 담았다" 의 10 % 를 넘으면 1 의 실패와 같이 본다
- 캐시가 하루에 앞값(110 MB)보다 크게 늘면 — 이웃 조각을 미리 담는 몫이다. 2–4 배까지는 정상이다(블록의 칸 넷 가운데 본 칸만 앞에서 담았다).
  v0.61.0(#286) 부터는 낸 칸을 두 벌 담지 않는다
- `WORKER TIMEOUT` 이 있으면 — gunicorn 은 `--threads 8 --timeout 60` 이라 한 요청이 오래 걸려도 워커가 죽지는 않아야 한다. 뜨면 큰 장을
  기다리는 스레드가 쌓인 것이다
- nginx 는 `proxy_read_timeout 90s` 다. 멕시코 지자기(문의 한계 90 초)는 잠금을 기다린 시간까지 더하면 504 가 날 수 있다. 서버는 끝까지 받아
  담으므로 **다음에 부르면 캐시에서 나온다** — 화면에서 한 번 빈 칸이 보이는 것은 알려진 몫이다

## 3. 이상하면 되돌리는 스위치

- **v0.61.0 부터** — `echo 1 > /srv/GSM/db/metatile_off`(또는 `.env` 에 `GSM_METATILE_OFF=1`) 하고 컨테이너를 다시 띄운다. 칸을 하나씩 받던
  앞의 길로 돌아가고, 미리 데우기도 메타타일 계획(`MetaPlan`)을 쓰지 않는다. 담아 둔 조각은 지우지 않는다 — 쓰이지 않을 뿐이다. 이 PR 에서 더했다
- **v0.60.0 에는 스위치가 없다** — 되돌리려면 이미지를 v0.59.0 으로 내린다. 그런데 0045 가 더한 응답 시간 열이 DB 에 기본값 없이 생겨서(SQLite 에서
  Django 는 `default` 를 열에 남기지 않는다) **v0.59.0 코드가 `UpstreamDay` 에 행을 넣지 못한다**. `usage.record` 가 오류를 삼키므로 화면은 돌지만
  **상류 호출 세기가 조용히 멈춘다**(차단 조짐으로 멈추는 것은 메모리에서 하므로 그대로 돈다). 이 PR 의 0046 이 열에 db 기본값(`db_default=0`)을
  둔다 — v0.61.0 부터는 v0.59.0 으로 내려도 센다
- 한 상류만 문제면 그 문의 `METATILE` 표에서 그 줄을 지우는 PR 이 가장 좁다

## 이 PR 에서 고친 것

- `settings.METATILE` — 끄는 스위치(위 3)
- 0046 — 응답 시간 열 열둘에 `db_default`. 옛 꼴의 `INSERT` 가 들어가는 것을 시험이 본다
- 손대지 않은 것 — 문의 시간 한계. 아일랜드만 20 초(나머지 45 초)지만 1 024 px 한 장이 3 초라 넉넉하다(287)
