# 시간 한계의 사슬 — 바깥이 안보다 길게, 넘으면 "느리다" 안내 타일

2026-10-05 · `feature/timeouts` · wetherilli

판 세션이 맡긴 일이다. wetherilli 299 를 적다가 본 것 — nginx `proxy_read_timeout` 90 초와 멕시코 지자기 문의 한계 90 초가 같아서, 메타타일 잠금을
기다린 시간이 더해지면 브라우저가 nginx 의 504 를 받는다. 504 는 타일 자리를 까닭 없이 비운다.

## 규칙

```
nginx proxy_read_timeout 90 초  >  문 한계 UPSTREAM_TIMEOUT_MAX 60 초  +  메타타일 잠금 기다림 METATILE_LOCK_WAIT 20 초  +  여유 10 초
```

- 화면이 부르는 길의 문은 상류 한 번을 60 초보다 길게 기다리지 않는다. 넘는 것은 멕시코 지자기(90 초) 하나뿐이었다 — 60 초로 줄였다.
  1 024 px 한 장이 20 초 남짓이라(wetherilli 244·282) 넉넉하다
- **시험이 지킨다**(`test_timeouts`) — 문의 `timeout=`·`TIMEOUT =` 숫자가 60 을 넘으면 깨지고, nginx 설정을 읽어 바깥이 안의 합보다 긴지 본다.
  호스트·사람이 부르는 받기(바람·구름·해류·지진 목록·화산·고생태·PBDB, KIGAM 의 씨앗·5만 WFS·자료 API)는 화면을 타지 않으므로 뺀다
- gunicorn `--timeout 60` 은 고치지 않았다 — 스레드 워커(gthread)에서는 요청 한계가 아니라 워커가 살아 있는지 보는 것이다. 설정 옆에 그렇게 적었다

## 고친 것

- **잠금 기다림에 끝을 두었다** — 막는 `flock` 에는 한계가 없어, 같은 큰 장을 받는 다른 요청이 오래 걸리면 기다리는 요청도 같이 늘었다.
  `LOCK_NB` 로 0.2 초마다 되묻고 20 초가 지나면 `metatile.Busy` 를 올린다. 받는 요청은 끝까지 받아 담으므로 다음에 부르면 나온다
- **늦은 메타타일은 칸 하나로 되받지 않는다** — 284 의 되받기는 큰 장이 실패하면 칸 하나를 다시 묻는다. 실패가 시간 초과면 60 초 + 45 초라
  바깥 한계를 넘는다. 시간 초과는 되받지 않고 올린다(EGDI 의 서비스 예외 같은 빠른 실패는 그대로 되받는다)
- **"느리다" 안내 타일**(`tiles.SLOW`, "GSM: upstream is slow - try again") — 상류의 시간 초과와 잠금 기다림을 "지도를 못 받았다"(`NO_MAP`)와
  갈라 낸다. 타일을 내는 열일곱 자리에서 같이 쓴다. 담지 않는다(`store=False`) — 다음에 다시 묻는다
- 늦은 것인지는 `metatile.slow(exc)` 가 본다 — 문이 감싼 오류의 `__cause__` 를 따라가 `requests` 의 `Timeout` 이 있는지. 뷰는 `requests` 를
  들이지 않으므로(문만 쓴다) 갈래의 이름과 모듈로 본다

## 남은 것

- `requests` 의 `timeout` 은 한 번 읽기의 한계라, 상류가 조금씩 흘려 보내면 전체는 더 걸릴 수 있다. 지금까지 그런 상류는 보지 못했다
- 타일 하나에 상류를 두 번 묻는 문(인도 GSI 의 그림과 누른 자리처럼 길이 둘인 것은 누른 자리 쪽)은 이 사슬을 두 번 쓸 수 있다. 타일 길에서 그런 문은
  찾지 못했지만 시험이 잡지는 못한다
