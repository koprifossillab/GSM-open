# 레이어가 오백을 넘은 뒤의 성능 점검

2026-10-05 · `feature/catalog-perf` · wetherilli

판 세션이 맡긴 일이다 — 레이어 616(켠 것 570)·레이어군 161 이 된 뒤 첫 화면이 받는 카탈로그, 지역별 거르기, map.js 의 첫 그림, 3D·prewarm 의
비용을 재고, 쓸데없이 무거운 곳만 고친다. 화면 동작은 바꾸지 않는다.

## 잰 값 (dev 서버, sqlite, 이 서버에서)

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| `_catalog` (서버) | 100–125 ms, 물음 163 | 11–14 ms, 물음 2 |
| 지도 화면 `/GSM/map/` (서버) | 120–210 ms | 17–19 ms |
| 3D 화면 `/GSM/3d/` (서버) | 250 ms | 18 ms |
| 첫 화면의 proj4 (브라우저, CPU 프로파일) | 129 ms | 55 ms |
| map.js 자신 (브라우저, CPU 프로파일) | 16 ms | 14 ms |

- 카탈로그 JSON 은 262 KB(영어판 230 KB) — 지도 화면 284 KB, **gzip 47 KB**. 운영 nginx 가 HTML 을 gzip 해 준다(`Content-Encoding: gzip`
  확인). 가장 큰 몫은 출처(`attribution`, 67 KB — 서로 다른 것 88 개를 465 번 되풀이)·설명 39 KB·범위 22 KB 인데, 되풀이라 gzip 이 거의 다 걷는다
- **화면은 이미 지역마다 거른다** — 레이어 패널이 그리는 줄은 지역의 것뿐이다(한국 82·남미 묶음 55·유럽 56·일본 65). JSON 을 읽는 값(262 KB)은
  몇 ms 다
- prewarm 은 부른 레이어만 한 번에 물어 계획한다(물음 하나). 1 초에 한 장씩이라 계획의 비용은 보이지 않는다
- 타일 요청마다 레이어의 상류를 묻는 `_upstream_of` 는 330 µs — 기본 차례(`group__order`) 때문에 레이어군을 잇지만 차례를 빼도 310 µs 라
  두었다

## 고친 것

1. **카탈로그의 N+1** — `prefetch_related("layers")` 로 미리 받고는 레이어군마다 `group.layers.filter(enabled=True)` 를 다시 불러 미리 받은 것을
   버렸다. 레이어군이 늘수록 물음이 늘어 160 을 넘었다. 켠 레이어만 `Prefetch(…, to_attr=…)` 로 한 번에 받는다. 차례는 Layer 의 기본 차례 그대로라
   레이어군 안의 줄 차례가 같다(시험이 본다). 지도·3D·`catalog/` 가 다 이 함수 하나를 쓴다
2. **3D 가 카탈로그를 두 번 지었다** — 고르개와 커스텀 지질도가 따로 불렀다. 한 번 지어 둘이 같이 훑는다
3. **3D 의 `<option>` 오백여 개를 템플릿이 돌렸다** — `{% if %}` 여섯을 레이어마다, 이 화면 시간의 절반이었다. 파이썬이 같은 `conditional_escape`
   로 짓는다(`views._options_3d`). 고치기 전후의 3D HTML 을 한국어·영어판 모두 떠서 견주니 한 글자도 다르지 않았다
4. **proj4 를 세 번 알렸다** — `ol.proj.proj4.register` 는 아는 투영의 모든 짝에 변환을 다시 짓는데, 정의를 더할 때마다(3413·3031 → 5179 들 →
   3978) 불렀다. 정의를 다 한 뒤 한 번만 부른다. 범위(`setExtent`)는 그 뒤에 그대로 건다

## 하지 않은 것

- **지역별로 나눠 받기·늦게 받기** — 47 KB(gzip)에 서버 18 ms 라 얻을 것이 적고, 화면이 다른 지역의 레이어를 아는 곳(묶음의 `includes`·`borrow`,
  지역을 바꿀 때의 기억, `#l=` 공유 링크)을 모두 비동기로 바꿔야 한다. 레이어가 지금의 두세 배가 되면 다시 본다
- **카탈로그를 프로세스 메모리에 담기** — 14 ms 라 무효화(관리 화면의 제목 손질, `verify_layers`)를 짊어질 까닭이 없다
- 브라우저의 페이지 전체 스크립트 시간(`ScriptDuration`)은 같은 화면도 130–400 ms 로 흔들렸다 — 이 서버의 헤드리스 브라우저가 밖의 타일을 받지 못해
  실패한 요청의 처리가 섞인다. 그래서 고친 값은 CPU 프로파일(파일별 자기 시간)로 적었다
