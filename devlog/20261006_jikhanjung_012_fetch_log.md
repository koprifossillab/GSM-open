# 받은 차례의 기록 — `store.sqlite` 의 `fetch_log` (P02 2 단계)

2026-10-06 · `feature/fetch-log` · jikhanjung

jikhanjung P02 의 2 단계. 받아 두는 자료원마다 **받은 차례 하나가 한 줄**인 기록 표를 `<DB 옆>/store.sqlite` 에 세웠다. 1 단계의
명세(사람이 정하는 것)와 짝이다 — 여기는 돌아가며 바뀌는 것(언제·결과·걸린 초·마지막 말·센 수 대 받은 수·원본 자리와 sha)만.

## 1. 무엇을 정했나

1. **명령 마흔다섯을 고치지 않고 한 자리에서 감쌌다** — `apps.py` 가 `BaseCommand.execute` 를 감싸 `viewer` 의 `fetch_*`·`build_*` 가
   끝날 때 한 줄을 적는다. 하나하나 고치면 빠뜨리는 것이 생기고, 새 명령은 저절로 들어온다. 자료원은 명세의 `commands` 로 찾고, 명세에
   없는 명령은 명령 이름을 자료원으로 적는다. 명령의 출력은 그대로 흘려보내며 **마지막 줄**만 기억해 `note` 로 남긴다
2. **명령은 아는 것을 `fetchlog.note()` 로 보탠다** — 이번에는 둘만: kigam50k(상류가 센 수 대 받은 수, 원본 날짜 폴더, 같은 판이면
   `changed=0`), PBDB(구운 곳 수, 원본 CSV 의 자리·sha). 나머지는 손댈 일이 생길 때. 칸이 비어도 장부는 선다
3. **장부가 일을 막지 않는다** — 기록이 실패하면 조용히 넘어간다. 예외는 `fail` 과 까닭을 적고 **다시 던진다**(명령의 결과를 바꾸지 않는다)
4. **호스트는 sqlite 에 쓰지 않는다**(검토의 "잠금") — `run.sh` 가 `GSM_RUN_PLACE=host` 를 건다. 매시 일은 지금처럼 `hourly_status.json` 이
   남기고, 사람이 호스트에서 부른 일(ERA5·ECCO2)은 `fetch_log_host.jsonl` 에 한 줄을 덧붙인다(한 줄 덧붙이기는 쪼개지지 않는다).
   컨테이너가 `sync()` 로 옮겨 적는다 — (자료원·시작한 때·어디서)가 같으면 두 번 적지 않는다. 매시 일은 JSON 에 마지막 차례만 있어
   **지난 차례는 사이가 빈다** — 늦었나만 보면 되므로 그것으로 됐다
5. **명세가 바뀌면 기록 표에도 한 줄**(자료원 `_spec`) — 1 단계의 떠 두기와 같은 때
6. **처음 채우기** `sources_backfill` — 빈 표로 시작하면 화면이 "모름" 투성이다. 산출물 파일의 고친 날로 `estimated=1` 한 줄씩. 저장소에
   굽는 것(`data/…`·`static/…`)은 이미지를 지은 날이 고친 날이라 어림하지 않았다
7. **시험에서는 끈다**(`FETCH_LOG`, `manage.py test` 면 꺼짐) — 시험이 부르는 명령이 개발 장비의 장부(저장소 뿌리의 `store.sqlite`)에 쌓이지 않게
8. **보기는 `sources_log`** — 화면(3 단계)이 서기 전까지 사람이 보는 길. 이름을 `fetch_log` 로 지었다가 바꿨다 — `fetch_` 로 시작하면
   기록 대상이 되고 씨앗 검사(모든 `fetch_*` 가 어느 자료원에)에 걸린다

## 2. 버린 것

- **Django 모델로** — `GSM.db` 에 넣으면 주간 백업이 부풀고, 뒤의 적재(②)가 이 파일에 자료원마다 표를 더할 것이다
- **명령마다 `with record():`** — 마흔다섯을 고치고 새 명령에서 빠뜨린다
- **호스트도 sqlite 에** — 컨테이너와 한 파일에 쓴다. WAL 이면 대개 괜찮지만 호스트 venv 의 sqlite 판까지 맞춰야 한다
- 매시 일의 모든 차례를 남기기 — 시간마다 넷, 1 년에 3 만 5 천 줄. 쓸모(늦었나)에 비해 크다

## 3. 운영에 닿는 것

- `run.sh` — `GSM_RUN_PLACE=host`
- `weekly_backup.sh` — `store.sqlite` 를 GSM.db 처럼 sqlite 백업 API 로 떠서 tar 에, `fetch_log_host.jsonl` 도 담는다
- 배포 뒤 한 번 `manage.py sources_backfill`

## 4. 확인

- 시험 `test_fetchlog` 10 개 — 된 것·깨진 것·보탠 칸·마지막 말, 장부가 깨져도 명령이 돈다, 호스트는 sqlite 에 안 쓴다(매시는 아무것도,
  사람이 부른 것은 jsonl), 옮겨 적기를 두 번 하지 않는다, 진짜 명령(`fetch_kigam50k`)을 감싸 한 줄, 시험에서는 끈다, 명세가 바뀌면 `_spec`.
  전체 2 054 개 통과, 저장소 뿌리에 장부가 생기지 않는다
- 운영 파일을 읽기만 하며(장부·명세는 임시 자리) — `hourly_status.json` 에서 바람·구름·아라온호·최근 지진 넷을 옮겨 적었고,
  `sources_backfill` 이 산출물이 있는 31 곳을 어림했다. 판 목록·지명처럼 저장소에 굽는 넷과 `fetch_grportal`(캐시에 담는다)은 비어 있다

## 5. 검토 뒤에 고친 것 (#369, koprifossillab 의 검토, 같은 날)

여덟을 짚었고 모두 맞았다. 결함 일곱은 고치기 전 코드로 깨지는 시험을 하나씩 넣었다.

1. **호스트가 읽기만 해도 `store.sqlite` 를 만들고 썼다** — `latest()`·`history()` 가 쓰는 연결(`connect()`, 파일·표·WAL)을 열었다.
   읽기는 `reader()` 로 갈랐다 — 파일이 없으면 빈 것, 호스트는 `mode=ro`. 호스트에서 쓰는 연결을 열면 오류로 막는다
2. **호스트가 명세를 먼저 읽으면 `_spec` 줄이 영영 빠졌다** — 정각의 `hourly.sh` 가 이력만 뜨고(호스트는 sqlite 에 안 쓴다) 컨테이너는
   "이미 뜬 판" 이라 건너뛰었다. **호스트는 이력도 뜨지 않는다** — 컨테이너가 처음 보고 둘 다 적는다
3. **매시 일의 성공이 빠질 수 있었다** — `hourly_status.json` 의 마지막 차례만 옮겼다. 마지막 차례가 실패면 `last_ok` 도 옮긴다(걸린 초를
   모르니 끝난 때 그대로, 그렇다고 적는다). 그리고 `at` 은 끝난 때라 **걸린 초만큼 당겨** 시작한 때로 적는다
4. **권한 오류에 명령이 죽었다** — 옮겨 적기가 `sqlite3.Error` 만 잡았다. `OSError` 도 잡고, `sources_backfill` 은 호스트에서 부르면 멈춘다
5. **손으로 부른 매시 명령(`run.sh fetch_araon --past`)이 어디에도 안 남았다** — "매시 일이면 건너뛴다" 가 아니라 "`hourly.sh` 가 부른 것이면
   건너뛴다" 로. `hourly.sh` 가 `GSM_HOURLY_JOB=1` 을 건다
6. **장부 파일을 지우면 소리 없이 끊겼다** — 표를 지었다는 기억을 프로세스가 들고 있었다. 열 때마다 `CREATE … IF NOT EXISTS`(싸다)
7. **장부가 클수록 느려졌다** — `latest()` 는 창 함수로 자료원마다 마지막 줄만 뽑는다. 옮겨 적기는 연결 하나에 `executemany`·`total_changes`,
   jsonl 은 읽은 바이트 자리를 `fetch_log_meta` 에 두고 새 줄만(덜 적힌 마지막 줄은 다음 차례에, 파일이 줄었으면 처음부터)
8. 자잘한 셋 — PBDB 의 sha 는 뺐다(150 MB 를 한 번 더 읽는다, 원본을 날짜 폴더에 두는 4 단계에서). 원본 경로는 장부 옆이 아니라 `<DB 옆>`
   기준. kigam50k 가 새 판이면 `changed=1`
9. **3 을 고치며 생긴 겹침** (다시 검토) — 옮긴 성공 뒤에 실패가 오면 그 성공이 `last_ok`(끝난 때)로 한 줄 더 생겼다. 먼저 옮긴 줄은 `at` 을
   걸린 초만큼 당긴 시작한 때라 `UNIQUE` 에 걸리지 않았다. `hourly.sh` 가 `last_ok_seconds` 도 남겨 같은 시작한 때로 당긴다. 그것이 없는 옛
   상태 파일이면 끝난 때에서 `LIMIT`(900 초) 안쪽에 시작한 매시 성공이 이미 있는지 보고 건너뛴다
