# GSM 에서 오프라인 묶음 요청하기 — 요청·어림·staff 승인·일꾼 (P16 4 단계)

2026-10-21 · `feature/gsmpack-request`(3 단계 `feature/gsmpack-cli` 위) · wetherilli

P16 의 마지막 단계다. 지금까지 묶음을 굽는 길은 터미널(`manage.py build_offline_pack <박스>`, 3 단계부터는 `gsmpack bake`)뿐이었다.
이제 연구소 판의 화면에서 범위를 잡아 요청하면 staff 가 승인하고, 서버가 하나씩 구워 `/GSM/offline/` 목록에 올린다.

```
지도의 범위 팝업 ──"이 범위로 오프라인 묶음 요청"──▶ /GSM/offline/request/?bbox=…   레이어·줌을 고르고 "어림"
                                                        │ POST 요청 한 줄 (기다림)
관리 화면 "오프라인 묶음" 탭 ── staff 가 "승인" ───────▶ │ 승인됨 → 일꾼을 띄운다
build_offline_pack --queue ── 한 번에 하나 ───────────▶ │ 굽는 중 → 됨 / 실패
/GSM/offline/ 목록·요청 화면 ── 내려받기                ▼ <OFFLINE_DIR>/req<번호>-<날짜>.gsmpack
```

## 사람이 정한 것 (2026-10-21)

- **레이어는 카탈로그에서 자유롭게**(레이어마다 화면 줌 처음·마지막) — 나는 정해진 세트에서 빼기만 하는 쪽을 권했다. 사람은 자유롭게를 골랐다.
  그래서 처음 화면에는 진교 묶음(406)의 세트를 켜 두고, 나머지 KIGAM 타일 레이어와 VWorld 배경 다섯은 끈 채 둔다(`offlinereq.PRESET`)
- **박스는 도폭 하나 크기까지** — 한 변 0.3°(5만 도폭 0.25° × 0.17° + 둘레). 나는 0.5° 를 권했다. 넓은 곳은 요청을 나눠 낸다

## 왜 이렇게 했나

- **차례는 고른 차례가 아니라 정한 차례다**(`offlinereq.clean`) — 예산(200 MB)은 뒤의 레이어부터 덜어 낸다. 화면에서 VWorld 를 먼저 켰다고
  VWorld 가 앞서면 지질도가 덜린다. 스킬 1 절의 차례(지질도 → 도폭 틀 → VWorld → 그 밖)를 박스에 넣을 때 다시 세운다
- **속성(지층 면)은 5만·25만·100만 지질도에만 붙인다** — `layer_units` 가 아는 것이 그 셋이다. 엮은 레이어(층리 등 제외)는 DescribeLayer 가 낱레이어 이름을 몰라 뺐다
- **어림은 요청 화면에서 곧장**(`offline/request/estimate/`) — `--dry-run` 과 같은 `bake.Plan` 이다. 캐시만 세고 상류를 타지 않는다.
  넘치면 덜어 낼 레이어를 미리 말한다. 줌은 16 까지만 고른다. 17 을 열면 한 변 0.3° 에서 칸이 레이어마다 만 사천 개라 어림 한 번에
  캐시 파일을 수만 번 들여다본다. 더 가까이는 화면이 마지막 줌을 늘려 그린다(405)
- **로그인 없이 요청한다** — 이름 칸 하나다(연구실 안의 길, `GSM_PUBLIC` 이면 닫힌다). 거르는 것은 승인이다. 승인·거절은 staff 만 한다.
  로그인은 데이터소스 탭의 것(jikhanjung 020)을 같이 쓴다 — 계정 화면을 하나 더 두지 않았다. 승인할 때 박스를 고치려면 admin 에서 한다
  (P16 은 탭에서 고치게 적었지만 화면이 커져 미뤘다)
- **상태는 낱말을 갈랐다** — "승인"·"거절" 은 단추(하는 일), 상태는 "승인됨"·"거절됨". 한 낱말이 두 뜻을 겸하지 않게(CLAUDE.md "말을 고르는 규칙")

### 일꾼 — 한 번에 하나

- **웹이 띄우고 잠금이 지킨다** — 승인하면 웹이 `build_offline_pack --queue` 를 떨어뜨려 띄운다(`offlinereq.spawn`). 셸이 뒤로 보내고 곧장 끝나니
  일꾼은 gunicorn 워커의 자식으로 남지 않는다. 그래서 끝나도 좀비가 생기지 않는다. 일꾼은 `<OFFLINE_DIR>/.queue.lock` 을 flock 으로 쥐고,
  승인된 것을 하나씩 굽다가 남은 것이 없으면 끝난다. 이미 하나가 돌면 새로 띄운 것은 잠금을 못 쥐고 곧장 끝난다 — 도는 쪽이 새 승인까지 집어 간다.
  프로세스가 죽으면 flock 도 풀린다. 그래서 낡은 잠금 파일을 지울 일이 없다
- **끊긴 것부터 잇는다** — 배포로 컨테이너가 다시 뜨면 굽던 것이 "굽는 중" 에 남는다. `entrypoint-web.sh` 가 뜰 때 일꾼을 한 번 띄운다.
  일꾼은 "굽는 중" 을 먼저 집고, 받은 것은 parts.sqlite 가 안다(VWorld). KIGAM 은 서버 캐시에 있다
- **무엇으로 멈추든 상태를 적는다** — 키가 없거나 차단 조짐이면 "실패" 에 마지막 줄(키는 `redact` 로 지운다)을 적고 다음 것으로 간다.
  실패한 것은 staff 가 다시 "승인" 하면 줄을 선다
- **버린 것** — 호스트 cron(호스트는 `GSM.db` 를 열지 않는다, jikhanjung P03), 매시 일(`hourly.sh`)에 얹기(굽기 50 분이 매시 일을 막는다),
  웹 요청 안의 스레드(gunicorn 이 워커를 다시 띄우면 같이 죽고, 워커 셋이 저마다 돌린다)

**배포 전 확인에 한 줄이 는다** — 굽는 중인 요청이 있으면 recreate 가 그것을 끊는다. 이어 굽기는 되지만, 50 분짜리를 다시 받기 시작한다.
판 세션은 배포 전에 관리 화면의 탭이나 `<OFFLINE_DIR>/.queue.log` 를 본다.

## 덧붙임 — 어림의 무게 (판 세션이 짚었다)

판 세션이 "0.3° 박스를 z16 까지 여러 레이어로 고르면 어림 한 번이 몇 초" 라고 짚었다. 407·408·409 를 합친 판으로 운영 캐시(`/data/GSM/tiles`, 읽기만)를 놓고 쟀다 —
0.3° × 0.3°, 레이어 16 개 다 줌 10–16(가장 무거운 요청)이면 칸이 3 만 2 천–3 만 5 천이다.

| 자리 | 칸 | 캐시에 있던 것 | 처음 | 다시 |
|---|---|---|---|---|
| 장성(캐시가 많다) | 33 091 | 2 218 | 5.7 초 | 0.7 초 |
| 영월 | 33 778 | 256 | 2.7 초 | 0.5 초 |
| 삼척 | 35 053 | 323 | 2.5 초 | 0.6 초 |

- **상한은 두지 않았다** — 박스가 0.3° 로 막혀 있어 칸 수에 끝이 있다. 처음 한 번의 몇 초는 차가운 디스크에서 파일을 찾는 몫이고, nginx 한계(90 초)보다 한참 짧다
- **대신 어림이 캐시를 읽지 않게 했다**(`KigamSource.cached_size` → `tilecache.size`, 굽는 고리의 `bake.cached_size`) — `tilecache.get` 은 읽을 때마다
  "마지막으로 쓰인 때" 를 적는다(`os.utime`, `prune_tiles` 가 그것으로 고른다). 그대로 두면 어림 한 번이 수천 장을 "쓰인 것" 으로 만든다. 따뜻할 때의
  시간은 고치기 전과 같다(0.5–0.7 초) — 빠르게 하려는 고침이 아니다
