## 2. 스캔판이 있는데 왜 또 얹나

같은 지도지만 쓰임이 다르다.

- 스캔판(026)은 16 m/화소에 지층 기호·단층이 있다. 가까이 볼 때 낫다
- 음영판은 58.8 m/화소에 **기호가 없고 지형이 보인다.** 3857 줌 11 언저리까지 선명하다.
  멀리서 지형과 지질을 함께 보는 데 낫다

그래서 갈아 끼우지 않고 나란히 두었다.

## 3. 미리 잘라 둔다 — 요청마다 풀지 않는다

1 억 7 천만 화소 JPEG 를 풀면 500 MB 가 넘는다. 요청마다 풀 수 없고, 워커마다 들고
있을 수도 없다. GeoMAP(018)처럼 요청 때 그리는 길은 여기서 맞지 않는다.

- `manage.py build_peninsula` 가 PDF 에서 JPEG·좌표를 꺼내(공간 라이브러리 없이 정규식으로)
  z0–z7 을 WebP 로 자른다. 2 343 장, 29 MB, 24 초, 메모리 3.5 GB
- 서버는 파일을 내주기만 한다. 우리 디스크의 타일이라 캐시에 담지 않는다
- **5179 그대로 자르고 화면이 옮겨 그린다** — 026 의 카카오 격자와 같은 길이다. 3857 로
  다시 구우면 한 번 더 흐려진다. 격자는 카탈로그 행(`grid`)으로 화면에 알린다
- 흰 바탕은 투명하게 한다(밝고 무채색인 것). 줄일 때 가장자리가 희게 번지지 않게
  미리 곱한 알파(`RGBa`)로 줄인다. 원본의 해안선에 있던 흰 안티앨리어싱은 남는다
- WebP 를 고른 것은 크기 때문이다 — 투명을 품고 PNG 의 몇 분의 일이다. 운영 디스크가
  87% 차 있다(TODOs)

## 4. PDF 의 좌표를 그대로 믿지 않았다

스캔판(026)과 나란히 옮겨 그려 보니 음영판이 몇백 m 어긋났다. 어느 쪽이 맞는지 가리려고
**OSM 해안선에 둘 다 대 보았다** — 해안 일곱 자리에서 땅/바다 가림막을 ±25 화소
밀어 가며 가장 잘 겹치는 자리를 찾았다(한 화소 약 80 m).

| 자리 | 음영판 동 · 북 (m) | 스캔판 동 · 북 (m) |
|---|---|---|
| 부산 | +160 · +319 | −160 · −80 |
| 포항 | +144 · +433 | −288 · +72 |
| 삼척 | +199 · +332 | −133 · −66 |
| 태안 | −313 · +235 | 0 · −156 |
| 목포 | −137 · +480 | +137 · −137 |
| 인천 | −77 · +232 | +155 · +77 |
| 원산 | 0 · +454 | 0 · +76 |

스캔판은 흩어져 있고 한쪽으로 몰리지 않았다 — 1:100만 원도의 선 굵기(0.2 mm = 200 m)
안이다. 음영판은 **일곱 곳 모두 북쪽**이고(평균 355 m), 가로로는 동해안이 동쪽·서해안이
서쪽으로 벌어져 있다. 한 지도를 누가 QGIS 에서 손으로 맞출 때 생기는 꼴이다. 옛 측지계
(Bessel)를 잘못 옮긴 것이었다면 가로가 한쪽으로 몰렸을 것이다.

그래서 고쳤다. 가로는 한 줄(오차 = −1380.9 + 0.001343·x, 0.134% 늘어남)로, 세로는 한 값
(−355 m)으로 범위를 다시 잡았다. 세로에 기울기를 주면 남는 오차가 조금 줄지만(±125 → ±120 m)
뜻 없는 차이라 버렸다. 고친 범위로 잘라, **맞출 때 쓰지 않은 자리**에서 다시 쟀다.

| 자리 | 고친 뒤 동 · 북 (m) |
|---|---|
| 강릉 | −110 · +110 |
| 여수 | +57 · +57 |
| 부산 | 0 · 0 |
| 군산 | +1219 · +135 |

군산은 새만금·군산항 매립으로 해안선이 바뀐 자리다. 스캔판도 +1286 m 로 똑같이 어긋난다.

PDF 가 적은 범위는 `PDF_X0…` 로 남겨 두고 **판을 알아보는 데만** 쓴다
(`check_corners` — 다른 PDF 를 넣으면 멈춘다). 격자는 고친 `X0…` 로 짓는다. QGIS
프로젝트의 원본이 오면 고친 값을 버리고 그것을 믿는다.
