# 031 — 시료 고도(P03)와 3D 의 일본 지형: 표고 상류 셋, 그리고 극지가 쉬워진 까닭

2026-09-29 · sclee · "우리가 받는 API 가운데 3D 지형 자료를 주는 것이 더 있나" 를 훑었다.
쓸 만한 것이 둘 나왔고(PGC·국토지리원) 사람이 "둘 다 지어" 라고 했다.

## 2. PGC — 극지가 쉬워졌다

P03 은 극지를 "web 이미지 밖의 명령, GDAL(`/vsicurl/`)로" 가자고 했다. ArcticDEM·REMA 가
COG 파일로만 있다고 봤기 때문이다. 그런데 극지 배경을 받던 ImageServer 가 **한 점의 값**을
준다. requests 한 번이면 되고 GDAL 이 필요 없다.

**기본값이 타원체고인 것을 놓칠 뻔했다.** `identify` 도 `getSamples` 도 그냥 부르면 타원체고다
— Summit Station 3 254 m, McMurdo −39 m. `identify` 에 `Height Orthometric` 을 붙이면
3 210 m(알려진 해발 3 216 m)·14 m 가 온다. 그래서 극지도 해발로 받는다. P03 §8 의 "높이 기준을
맞출까" 는 상류가 풀어 주었다. `getSamples` 는 여러 점을 한 번에 받지만 이 함수를 듣지 않는다.
한 점에 한 번 묻고 0.2 초 쉰다. 그래서 화면에서는 극지 점 100 개까지만 채우고 넘으면 명령
(`fill_elevation`)으로 넘긴다.

## 3. 국토지리원 — 일본의 시료와 3D

후지산 꼭대기를 국토지리원은 3 774 m, AWS(SRTM)는 3 754 m 로 읽는다(알려진 값 3 776 m).
일본 안에서는 국토지리원이 낫다.

- **시료**: 일본 자리의 점은 z14 `dem_png` 에서 읽는다. 자료가 없으면 AWS 로 넘어간다.
  한국 동남해안·울릉도·독도는 경계 상자에서 빼 두었다. 물어도 404 라 헛걸음이다(404 도 캐시에 담는다)
- **3D**: 브라우저의 `transformRequest` 가 일본 자리(z14 까지)의 표고 타일만 우리 `dem/` 로
  돌린다. 서버는 국토지리원 인코딩(`x·0.01 m`, (128,0,0) 은 자료 없음, 2^23 넘으면 음수)을
  Terrarium 으로 옮긴다. **빈 칸은 같은 자리의 AWS 값으로 메운다** — 그대로 두면 (128,0,0) 이
  8 만 m 로 솟는다. 해안 타일은 4 분의 1 이 빈 칸이었다. 일본 밖은 AWS 로 302 한다
- MapLibre 4.7.1 에 `encoding: "custom"` 이 있지만 쓰지 않았다. 빈 칸을 지우는 셈이 없어
  어차피 서버를 한 번 거쳐야 한다
- 헤드리스 그림에 타일 경계가 보였다. 이웃 타일 끝 픽셀의 차이(z12 평균 1.7 m)가 타일 안쪽 한
  걸음과 같아 자료가 끊긴 것은 아니다. 음영이 이웃 타일을 다 받기 전에 찍힌 것으로 본다

## 4. 저장 — P03 §3 그대로

`Point.elev`·`elev_source`·`elev_datum`. `props` 에 넣지 않는다 — 원본의 `고도` 열(실측)과
섞이면 어느 것이 잰 것인지 가를 수 없다. GeoJSON 에는 `표고(DEM)`·`표고 출처` 로 싣고,
되살리기가 둘을 떼어 제 칸으로 돌린다. 출처 → 높이 기준의 표는 `elevation.SOURCES` 와
`pointsets.ELEV_DATUMS` 두 벌이다(`pointsets.py` 가 상류를 모르게 두려고). 시험이 둘을 맞춘다.

P03 §8 의 나머지 물음은 이렇게 정했다.
- **원본에 고도 열이 있어도 채운다.** 둘을 나란히 보면 GPS 고도가 틀린 점이 드러난다
- **단추는 실험 기능 밖에 둔다.** 3D 와 상관없이 쓸모 있는 일이다
