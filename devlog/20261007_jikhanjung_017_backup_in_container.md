# 주간 백업도 컨테이너를 거쳐 DB 를 뜬다

2026-10-07 · `fix/backup-in-container` · jikhanjung

"호스트가 DB 를 건드려야 할 필요가 있으면 컨테이너를 통해"(사람, 같은 날, jikhanjung 016)의 마지막 예외였던 주간 백업을 고쳤다. `weekly_backup.sh` 는
호스트의 python 으로 `GSM.db`·`store.sqlite` 를 sqlite backup API(읽기 전용)로 떴다. 판 세션이 #383 을 병합하며 짚었다 — 지금의 rollback 저널에서는
읽기 전용이면 괜찮지만 **WAL 로 바꾸면 읽는 쪽도 -shm 에 써야 하고 마지막 연결이 WAL 을 정리한다**. WAL 로 가기 전에 정리할 것이었다.

## 1. 무엇을 정했나

1. **`manage.py backup_db`** — 컨테이너 안에서 온라인 백업으로 임시 자리에 사본을 뜨고, `integrity_check` 를 지난 것만 **바이트째 표준 출력**으로 낸다
   (`--store` 면 store.sqlite). 호스트는 `docker compose exec -T … backup_db > 사본` 으로 받아 tar 에 담는다. 살아 있는 DB 는 컨테이너만 연다
2. **호스트는 받은 사본의 머리(`SQLite format 3`)만 본다** — 무결성 검사는 컨테이너가 이미 했다. 빈 파일·오류 글이면 머리가 맞지 않아 멈춘다
3. **사본을 DB 옆의 자리에 떨구지 않았다** — 컨테이너가 `/srv/GSM/db/.backup/` 에 쓰고 호스트가 옮기는 길도 있었지만, DB 옆에 파일이 생기면 ② 의
   목록(`find`)이 그것을 줍는다. 표준 출력이면 자리가 필요 없다
4. **컨테이너가 서 있지 않으면 백업은 실패로 끝난다** — 전에는 컨테이너가 멈춰 있어도 호스트가 떴다. 그 경우는 받기(⑤–⑦)도 못 하고 healthz 도 죽어
   이미 알린다. 원칙을 지키는 쪽을 골랐다
5. `MANAGE`(컨테이너의 manage.py)를 스크립트 머리로 올려 ①(사본)과 ⑤–⑦(받기)이 함께 쓴다

## 2. 확인

- 시험 `test_backup_db` 넷 — 표준 출력이 온전한 sqlite 한 장(다른 글이 섞이지 않는다), `--store`, 호스트에서는 멈춘다, 없으면 멈춘다. 전체 통과
- 운영 사본(GSM.db, 0049 까지)으로 `backup_db > 파일` — 머리·integrity_check·데이터소스 49 줄
- 운영 컨테이너에는 이 명령이 판이 나간 뒤에 생긴다 — **이 판이 배포되기 전에 주간 백업(월요일 01:40)이 돌면 옛 스크립트 사본**이 돈다
  (스크립트는 컨테이너가 뜰 때 `/srv/GSM/scripts/` 에 깔린다, koprifossillab 005). 둘이 함께 바뀐다

## 검토 뒤에 고친 것 (#385, koprifossillab 의 검토, 같은 날)

- **받은 사본에도 `integrity_check`** — 호스트는 머리(`SQLite format 3`)만 봤다. 명령이 0 으로 끝났는데 흘리던 바이트가 중간에 잘리면 머리만 멀쩡한
  사본이 "성공" 으로 남는다. `intact()` 가 받아 둔 사본을 한 번 더 연다 — 살아 있는 DB 가 아니라 받은 파일이라 "호스트는 GSM.db 를 열지 않는다" 와
  어긋나지 않는다. 온전한 사본은 지나고 반으로 자른 사본은 `database disk image is malformed` 로 걸리는 것을 봤다
