# 느린 상류 찾기와 메타타일 적용

2026-10-05 · `feature/metatile-3` · wetherilli

판 세션이 맡긴 일이다 — 느린 상류(평균 3 초 넘게)를 추려 메타타일(wetherilli 282·284) 표에 더한다. #273 위에 쌓았다.

## 운영에서는 잴 수 없었다

- `manage.py upstream_stats` 는 상류마다 하루의 성공·실패·차단 **수**만 센다(`UpstreamDay`) — 시간이 없다
- gunicorn 의 접근 로그(`--access-logfile -`)는 기본 꼴이라 걸린 시간이 없고, 문의 로그(`… -> 200`)도 시간을 적지 않는다. nginx 로그는 이 계정이 읽지 못한다.
  게다가 v0.58.0 배포로 컨테이너가 막 새로 떠 로그가 백 줄 남짓이었다
- 그래서 **이 서버에서 문으로 곧장 쟀다** — 3857 WMS 로 화면이 받는 상류마다 레이어 하나, 그 범위의 한가운데, 그리는 줌(격자 줌 6 언저리)의 512 px 한 칸,
  요청 사이 1.5 초. 걸린 시간을 남기려면 문의 로그에 시간을 붙이는 것이 다음 일이다(TODO 가 아니라 이 devlog 에만 적는다 — 판 세션이 정한다)

한 번이라도 3 초를 넘었고 1 024 px 한 장이 512 px 넷보다 확실히 싼 것을 넣었다. 1 024 px 가 512 px 보다 빠른 곳(segemar·dinamige·lneg)도 있다 —
그리는 값보다 요청마다 드는 값이 큰 상류다.

## 넣지 않은 것

- **cgs** — 자료를 파는 상류라 서버 캐시에 담지 않는다(`NO_STORE`, wetherilli 209). 메타타일은 조각을 캐시에 담으므로 맞지 않는다. 표의 시험이 막는다
- 3 초 언저리(bgsgi·esdm·sgm 지질도·brgm·georep·gsq) — 한 번 잰 값뿐이라 두었다. 다시 재어 늘 느리면 더한다
- gsj·gsitile·ingemmet 따위 z/x/y 타일과 3857 가 아닌 상류(NPI·NGU 따위 지역 투영)는 메타타일 길(3857 격자)에 맞지 않는다

문마다 `METATILE` 한 줄(284 의 꼴) — `austates`(gssa)·`iige`·`ispra`(1:100만)·`mris`·`pig`·`sgs`·`dinamige`·`lneg`(1:50만)·`tno`·`swisstopo`·`segemar`·`gsi`(1:100만).
모두 모든 줌이다. prewarm 은 284 의 `MetaPlan` 으로 이 레이어들도 2 × 2 블록으로 데운다. 시험(`test_metatile.Table`)이 표의 줄마다 카탈로그에 걸리고 3857 WMS 이고
`NO_STORE` 가 아닌지 본다.
