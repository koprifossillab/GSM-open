# 백업 사본의 로그인 세션, 같은 날 두 번째 백업

2026-10-07 · `fix/backup-sessions` · jikhanjung

공통 규약(`.guides/web/data-safety.md`, CLAUDE.md "공통 규약")과 GSM 의 주간 백업을 견줘 걸린 둘.

## 1. 사본에서 로그인 세션을 지운다 (§7)

주간 백업의 `GSM.db` 사본은 누구나 읽는 NAS(777)로 간다. 오늘 탭 안의 로그인과 staff 계정이 생겨(jikhanjung 020) `django_session` 에 세션이
쌓이기 시작했다 — **세션 키가 곧 쿠키 값**이라 사본을 읽은 사람은 그대로 로그인된다(`SECRET_KEY` 가 달라도). `backup_db` 가 사본의
`integrity_check` **뒤에** 세션을 비우고 VACUUM 한다(빈 페이지에 남지 않게). 순서를 뒤로 둔 것은 깨진 원본의 VACUUM 이 예외를 내 검사를 덮지
않게다. 비밀번호 해시는 둔다 — 되살릴 때 계정이 있어야 한다. 살아 있는 DB 의 세션은 건드리지 않는다.

같은 자리에서 **사본의 저널을 DELETE 로**(§5) — 사본은 원본의 저널 모드를 물려받는다. 뒤에 원본을 WAL 로 바꿔도(사람이 "나중에") 사본은 파일 하나다.

## 2. 같은 날 두 번째 백업은 `.2` (§16)

① 의 이름이 `GSM.<날짜>.tar.gz` 하나뿐이라 같은 날 `--backup-only` 를 한 번 더 돌리면 그날 아침의 사본(받기 전의 것)을 로컬·NAS 둘 다
덮었다 — 규약의 실제 사례와 같은 꼴이다. `free_name` 이 로컬이나 NAS 에 이미 있으면 `.2`·`.3` … 을 붙인다. ② 도 같다. ② 를 줄이는 `prune_built`
와 "가장 새 ②" 를 찾는 줄은 `.2` 도 세고, 이름이 아니라 시각순으로(같은 날의 둘째가 그날의 대표, §10).

## 3. 확인

- 시험 — 사본에 세션이 없고(VACUUM — 쿠키 값이 바이트에도 없다) 계정은 있고 저널은 delete, 살아 있는 DB 의 세션은 그대로. 스크립트의 두 함수를
  꺼내 bash 로 — 같은 날 셋째는 `.3`, 줄이기는 달마다 가장 새 것(같은 날의 `.2`)을 남긴다. 고치기 전 코드로 셋 다 깨진다. 전체 통과
- 운영 사본(세션 넷)으로 `backup_db` — 사본의 세션 0·계정 1·delete·integrity ok
