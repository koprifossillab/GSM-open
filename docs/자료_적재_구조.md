# 받아 두는 자료 — 원본·적재·굽기를 가를까

2026-10-06 · koprifossillab · 검토 (계획이 아니다)

[외부_자료원.md](외부_자료원.md) 를 모으다 보니 **받는 일(cron·사람)과 받은 것을 우리 안에서 다루는 일이 자료마다 따로** 놀았다.
상류의 꼴과 조건, 갱신되는 자료를 DB 에 두고, 웹에는 거기서 구운 JSON 따위를 내려주는 **한 가지 절차**로 묶을 수 있나를 따진다.
중계하는 상류 여든 남짓(요청이 올 때 받아 캐시에 보태는 것)은 갱신이라는 게 없어 여기서 다루지 않는다 — 받아 **모아 두는** 것만이다.

**모으려는 까닭은 관리 화면이다.** 자료원마다 조건·주기·마지막으로 받은 때·결과·행 수·구운 판을 `/GSM/manage/` 의 **한 줄**로
일목요연하게 보고 싶다. 지금은 그 한 줄을 그릴 재료가 여러 곳에 흩어져 있어, 화면을 먼저 만들 수가 없다 — 그래서 재료를 한 자리에 모으는 것부터 따진다.

## 지금의 모습

자료 하나에 대한 것이 여러 곳에 흩어져 있다.

| 자료 하나에 대한 것 | 사는 곳 |
|---|---|
| 조건·비상업·CORS | `docs/상류_조건표.md` (손으로) |
| 언제 받나 | `deploy/scripts/hourly.sh` 의 `JOBS` — 나머지는 사람이 기억한다 |
| 마지막으로 됐나 | `<DB 옆>/hourly_status.json` (매시 일만) |
| 무엇이 있고 언제 구웠나 | `datastatus.ITEMS` — 파일 `stat` 과 머리 4 KB 로 **어림한다** |
| 상류에 얼마나 묻나 | `UpstreamDay` (Django DB) |

**받기와 굽기가 한 명령 안에 붙어 있다.** `fetch_pbdb` 는 CSV 를 받아 `<EARTH_DIR>/pbdb_collections.csv` 에 남기고, 곧장
`fossils.build()` 가 그것을 다듬고·판을 붙이고·R*Tree 색인을 지어 `pbdb.sqlite` 하나로 낸다. 그 파일이 **저장소이자 화면이 읽는
산출물**을 겸한다. 지진(`quakes.csv` → `quakes.sqlite`)·Neotoma·지열류·응력·광상·빙하가 같은 틀이다.

- 원본은 남지만 **날짜 없이 덮어쓴다** — 지난번 받은 것과 견줄 수 없다
- 다시 받을 때 **통째로** 받고 통째로 굽는다. PBDB 는 110–160 MB, 몇 분
- 임시 파일에 굽고 바꿔치기하는 손(`.building` → `tmp.replace`)을 일곱 모듈(fossils·quakes·paleoeco·heatflow·stress·minerals·glaciers)이
  저마다 따로 갖는다
- `meta` 표의 열쇠가 파일마다 다르다 (2026-10-06 운영에서 읽음)

  | 파일 | `meta` 열쇠 |
  |---|---|
  | pbdb·quakes·stress·glaciers·heatflow | built·license·rows·source |
  | minerals | 위 + counts |
  | neotoma | built·datasets·license·sites·source (rows 없음) |
  | moon·mars·mercury 원도, sim3534 | renderer 뿐 |
  | mars_craters, taiwan_open/sensitive | `meta` 없음 |

  **상류 자료의 판과 받은 때는 어느 파일에도 없다** — 구운 날(`built`)만 있다

## 세 단계로 가르자

| 단계 | 하는 일 | 꼴 | 바뀌는 것 |
|---|---|---|---|
| **① 원본** | 상류가 준 것을 **그대로**, 받은 날짜마다 | 파일 `<DB 옆>/raw/<자료원>/<날짜>/` | 쌓인다. 사람이 `prune` 으로 줄인다 |
| **② 적재** | 다듬어서 **DB 하나**에 — 자료원마다 표, 그리고 공통 기록 표 | sqlite 한 파일 | 자료원마다 트랜잭션. 가능하면 바뀐 행만 |
| **③ 굽기** | ②에서 읽어 웹이 쓸 것(JSON·타일·색인 파일)을 | 파일, 바꿔치기 | ②가 바뀌었을 때만 |

앞서 "sqlite 를 하나로 합치지 말자" 고 든 까닭 — 파일째 바꿔치기, 파일 mtime 으로 무효화하는 읽기 캐시, 공개 여부를 파일로 가르기 —
은 **③ 산출물의 이야기**였다. ②를 하나로 두는 것을 막지 않는다.

②를 하나로 두면 얻는 것.

- **장부가 자료 옆에 산다** — 언제 받았나·몇 행인가·어떤 조건인가가 SQL 한 줄이다. `datastatus` 가 어림할 일이 없어진다
- **증분이 된다** — 번호(`collection_no`·지진 id)로 upsert 하고 바뀐 행에 표시한다. 굽기는 바뀐 것이 있을 때만
- **자료끼리 엮기** — `pointvalues`(점마다 가까운 PBDB 산지 따위)가 같은 DB 에서 묻는다

## 모든 자료가 ②를 거치지는 않는다

| 갈래 | 예 | 길 |
|---|---|---|
| **행 자료** | 화석·지진·Neotoma·지열류·응력·광상·빙하·화산·극지연구소 목록·KIGAM 자료 | ①→②→③. 화면이 bbox 로 그때그때 묻는 것이라 ②에 공간 색인이 있으면 ③이 거의 없다 |
| **격자·래스터** | 바람·해류·위성 구름·IBCSO·ADMAP·해양 지각 연대·방사능 | ①→③. DB 에 넣을 까닭이 없다. **기록 표에는 한 줄** 올린다 |
| **면 자료** | 달·화성·수성 원도, 카리브, GeoMAP | 사이. ②에 넣을 수는 있지만 얻는 게 작다 — 지금 길을 두고 기록 표에만 |
| **판과 함께 오는 씨앗** | `data/*.json` (Natural Earth·PALEOMAP 따위) | 저장소에 든다. 여기서 다루지 않는다 |

**① 원본의 본보기가 이미 하나 있다 — KIGAM 5만 구조 요소(`fetch_kigam50k`, jikhanjung P01·wetherilli 199).** WFS 에서 받은 그대로를
`<DB 옆>/kigam50k/raw/<YYYYMMDD>/<레이어>.geojson.gz` 로 날짜마다 두고, 그 폴더의 `manifest.json` 에 레이어마다 요청 주소·상류가 센 수
(`numberMatched`)·받은 수·바이트·sha256 을 적는다. **받은 수가 센 수와 같을 때만** 적고, sha256 이 앞 판과 같으면 새 폴더 없이 확인한 날만
남긴다. 화면(`kigam50k.py`)은 가장 새 날짜 폴더를 읽는다(②③ 없이). 기록 표의 `fetched_at`·`rows`·`raw_path`, 그리고 "상류가 일부만
준 것" 을 가리는 칸(센 수 대 받은 수)을 정할 때 견줄 만하다.

**기록 표는 셋 모두에 걸친다** — ②를 거치지 않는 자료도 장부에는 오른다. "흩어져 있다" 는 문제의 대부분은 이 표 하나가 푼다.

## 공통 기록 표의 칸 (초안)

자료원 하나·받은 차례 하나가 한 줄이다.

| 칸 | 뜻 |
|---|---|
| `source` | 자료원 id (`pbdb`·`quakes`·`gfs` …) — 명세 표의 열쇠 |
| `fetched_at` | 받은 때 |
| `upstream_version` | 상류가 밝힌 판 (없으면 빈칸 — 받은 날이 판이다) |
| `raw_path` | ① 원본의 자리 |
| `rows` · `changed` | 적재한 행 수, 그 가운데 바뀐 것 |
| `result` · `note` | 된·안 된, 사람에게 한 말 마지막 줄 (지금 `hourly_status.json` 의 것) |
| `seconds` | 걸린 초 |
| `built_at` · `built_by` | ③을 구운 때, 구운 명령과 그리는 법의 판 |

**조건·주기·돌리는 곳(호스트 venv 인가 컨테이너인가)은 이 표에 두지 않는다.** 사람이 정하는 것이라 명세(JSON, 아래 "명세는 JSON 으로")에
둔다. DB 에는 **돌아가며 바뀌는 것만** 둔다.

## 명세는 JSON 으로 — 지향하고, 차근차근

(2026-10-06 사람이 정함.) **시스템이 바뀐 것이 없고 자료만 바뀌었는데 PR·시험을 거치는 것은 이상하다.** 자료원의 조건을 고치거나
주기를 바꾸는 것은 코드가 아니라 자료를 고치는 일이다. 그래서 명세는 파이썬 표가 아니라 **JSON 을 지향한다.**

- **지금 있는 파이썬 표는 그대로 둔다** — `datastatus.ITEMS`·`static_site.UPSTREAMS`·`views.LAB_ONLY`·`views.NO_STORE` 따위.
  급하지 않다. 손댈 일이 생길 때 하나씩 JSON 으로 옮긴다
- **새로 만드는 명세(자료원 표)는 처음부터 JSON 이다**
- 파이썬 표가 거저 주던 것은 JSON 에서 따로 챙긴다
  - 칸이 틀리거나 빠진 것 — 읽을 때 검사해서, 틀린 줄은 건너뛰고 관리 화면에 띄운다(뷰어는 멈추지 않는다)
  - 영어판 — 카탈로그의 `LAYER_EN` 처럼 이름 칸을 두 말로 적거나, `i18n_missing` 이 이 JSON 도 긁게 한다
- 남는 물음 — **JSON 을 어디에 두나**
  - 저장소 `data/` 에 두고 **문서처럼 `main` 에 바로** 커밋한다 — git 이력이 남고 PR 은 거치지 않는다. 다만 판을 다시 굽기 전까지
    운영에 닿지 않는다
  - `<DB 옆>` 에 두고 관리 화면에서 고친다 — 곧장 운영에 닿는다. 대신 이력은 따로 남겨야 한다(고친 사람·때를 기록 표 옆에)

`UpstreamDay` 는 그대로 둔다 — 상류에 **몇 번 물었나**(호출 제한을 지켜보려는 것)이고, 이것은 **무엇을 받았나**다.

## 관리 화면에서

지금 관리 화면에는 이 일에 걸친 탭이 둘 있다 — "상류 응답 시간"(`UpstreamDay`, wetherilli 295)과 "구운 자료"(`datastatus`, wetherilli 312).
매시 일의 결과(`hourly_status.json`)는 healthz 만 읽고 화면에는 없고, 조건은 문서에만 있다. 같은 자료원이 두 탭에 다른 이름으로 오르기도 한다
(`fetch_pbdb` 로 받은 것이 "구운 자료" 에서는 `earth/pbdb.sqlite`).

명세 표와 기록 표가 생기면 **"자료원" 탭 하나**가 된다. 자료원 하나가 한 줄이다.

| 칸 | 어디서 |
|---|---|
| 자료원·기관 | 명세 |
| 조건 (라이선스·비상업·공개 여부) | 명세 |
| 주기·돌리는 곳 (매시 cron·사람·호스트 venv·컨테이너) | 명세 |
| 마지막으로 받은 때·결과·걸린 초·마지막 말 | 기록 표의 마지막 줄 |
| 마지막으로 **된** 때, 늦었나 (주기보다 오래 안 됐으면 붉게) | 기록 표 + 명세의 주기 |
| 상류 판·행 수·바뀐 행 | 기록 표 |
| 구운 판·산출물이 있나·크기 | 기록 표 + 파일 `stat` |
| 상류에 물은 수·차단 조짐 (오늘·7 일) | `UpstreamDay` |

줄을 누르면 그 자료원의 받은 차례들(기록 표의 지난 줄)이 펼쳐진다 — 행 수가 갑자기 줄었다든지(상류가 일부만 준 것) 하는 것을 거기서 본다.
"상류 응답 시간" 탭은 중계하는 상류 여든 남짓 때문에 따로 남는다. "구운 자료" 탭은 이 탭에 녹는다.

**화면은 처음에 읽기만 한다.** "지금 받기" 단추는 웹 요청이 몇 분짜리 받기를 띄우는 것이고, 호스트 venv 에서 도는 일(바람·구름)은
컨테이너가 부를 수도 없다. 단추를 둘지는 아래 "사람이 정할 것" 에 둔다.

## 어느 DB 에

- **sqlite 한 파일** (`<DB 옆>/store.sqlite`) — 지금 그대로의 틀이고 서비스가 늘지 않는다. 쓰기가 하나씩이라 **적재는 한 곳에서만** 한다.
  호스트 cron(바람·구름)과 컨테이너가 같은 파일에 쓰지 않게 — 격자 자료는 어차피 ②를 거치지 않으니 호스트는 기록 표에 한 줄만 쓴다.
  그 한 줄도 잠금이 걱정이면 호스트는 지금처럼 상태 JSON 을 쓰고 컨테이너가 옮겨 적는다
- **PostGIS** — 공간 질의·동시 쓰기가 자연스럽다. 대신 운영할 서비스가 하나 늘고 백업이 바뀐다

행 자료는 합쳐 수백만 행 아래다. **sqlite 한 파일로 충분해 보인다.** PostGIS 는 동시 쓰기가 실제로 부딪힐 때 다시 본다.

## 버린 것

- **Django 의 `GSM.db` 에 넣기** — 사람이 만든 점묶음·카탈로그가 사는 DB 이고 마이그레이션·주간 백업의 대상이다. 다시 받을 수 있는
  수백 MB 가 섞이면 백업이 수백 배가 된다. 저장소(②)는 따로 둔다
- **산출물(③)까지 한 파일로** — 위에서 본 대로 바꿔치기·캐시 무효화·공개 여부 가르기가 파일 단위다
- **담는 꼴을 하나로** — 화석은 R*Tree, 바람은 PNG 텍스처, IBCSO 는 미리 자른 타일. 저마다 까닭이 있다. 맞출 것은 **장부와 절차**다

## 해 본다면

1. **화석·지진 둘로 ①②③을 시범한다.** 둘 다 받은 CSV 가 이미 남고(`--csv` 로 다시 굽기가 된다) 번호가 있어 증분을 시험하기 좋다.
   화면이 읽는 길(`fossils.points`·`quakes.*`)이 ②를 곧장 읽게 할지, ③으로 지금 꼴의 파일을 구울지도 이때 잰다
2. 틀이 맞으면 나머지 행 자료를 옮긴다
3. 격자·면 자료는 지금 길을 두고 **기록 표에 줄만** 올린다. `datastatus` 와 `hourly_status.json` 이 이 표를 읽게 바꾼다
4. 관리 화면의 "자료원" 탭 — 1 과 따로 갈 수도 있다. 명세 표와 기록 표만 있으면 ②의 적재가 시범 둘뿐이어도 모든 자료원의 줄이 선다.
   **화면이 목적이라면 명세·기록 표 → 화면을 먼저 하고, 적재(②)는 그 뒤에** 가는 차례가 더 빨리 쓸모가 난다

## 사람이 정할 것

- ②를 화면이 곧장 읽을까, ③을 늘 둘까 — 곧장 읽으면 단계가 줄지만 적재 중의 쓰기와 화면의 읽기가 한 파일에서 만난다(WAL 이면 대개 괜찮다)
- ① 원본을 얼마나 둘까 — PBDB 한 벌 150 MB 남짓. 최근 몇 벌만 둘지, 판이 바뀔 때만 둘지
- 명세 JSON 을 저장소 `data/` 에 둘까 `<DB 옆>` 에 둘까 (위 "명세는 JSON 으로")
- 관리 화면에 "지금 받기" 단추를 둘까 — 둔다면 컨테이너에서 도는 일만, 받기는 뒤에서 돌리고 화면은 기록 표를 다시 읽는다
